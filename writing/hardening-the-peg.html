1. RewardManager: cooldown gate checked against msg.sender instead of to

  • Commit: 8d0bb4b (2024-06-22)
  • File: contracts/XSD/Pools/RewardManager.sol
  • Category: confused deputy

userProvideBankXLiquidity, userProvideXSDLiquidity, and LiquidityRedemption each take an explicit to beneficiary parameter, separate from msg.sender, so a relayer or router can submit on a user's behalf. Each function gates on a per-address cooldown flag set by PIDController.priceCheck(), then clears it. Both the check and the clear used msg.sender.

Before:

After:

Same substitution applied in userProvideXSDLiquidity and LiquidityRedemption.

Root cause: principal mismatch. Code is correct only when to == msg.sender; any call through an intermediary checks and clears the wrong address's state.

Impact if unfixed: a relayed call for a beneficiary who hadn't primed their own price-check reverts with "must wait" regardless of correctness. Conversely a relayer with a primed flag could push a call through and clear the relayer's own flag, leaving the real beneficiary's cooldown gate armed for a payout that already happened under someone else's state.

Also in this commit: the repeated inline require(msg.sender == smartcontract_owner, ...) across roughly six admin functions was consolidated into a single onlyByOwner modifier.

2. XSDStablecoin.pool_price(): division before scaling

  • Commit: 3264a85 (2024-09-15)
  • File: contracts/XSD/XSDStablecoin.sol (pool_price())
  • Category: fixed-point math

Before:

After:

Token ordering (verified): both XSDWETHpool.sol and BankXWETHpool.sol hardcode token0 as the protocol token (XSD/BankX) and token1 as WETH, in their constructors, not Uniswap's address-sort convention. This ordering holds by construction on every deployment of a given pool contract.

Root cause: reserve0/reserve1 is therefore a tokens-per-WETH ratio, ordinarily large (thousands), since one XSD or BankX token is worth a small fraction of one WETH. Integer division on a large ratio drops only the fractional remainder, a small precision loss that grows proportionally as the ratio shrinks. In thin or newly-seeded liquidity, where the ratio can fall below 1, it truncates to exactly 0. The existing if (reserve0 == 0 || reserve1 == 0) return 1; guard covers zero reserves, not a zero ratio, so _eth_usd_price / price_vs_eth then divides by that zero and reverts.

Impact if unfixed: the normal-liquidity case is silent precision drift, no revert, just plausible-looking numbers. The thin-liquidity case is a revert propagating to every caller of pool_price(): collateral-ratio math, mint/redeem pricing, interest calculations.

Redemption has a mandatory block_delay between request and collectRedemption(). Credit side (redeemInterestCalc, 7a15bae):

Fix: fix the token amount once at request time in redeemBankXTokenBalances; collectRedemption() reads the precomputed figure with no second price lookup.

5. CollateralPool collateral-availability check: dollar reserve subtracted from a WETH balance

  • Commit: abb17d6 (2024-12-31)
  • File: contracts/XSD/Pools/CollateralPool.sol
  • Category: unit mismatch

Before:

After:

Root cause: unclaimedPoolCollateral is a dollar-denominated reserve (1e18 scale, per fd516b4: weth_dollar_value = (neededWETH * eth_usd_price())/1e6 // precision of 1e18), subtracted directly from a raw WETH token balance. eth_usd_price() is 1e6-scaled dollars-per-WETH (PRICE_PRECISION = 1e6). Dimensional check on the fix: (dollars_1e18 * 1e6) / price_1e6 = dollars_1e18 / price_raw * 1e6 reduces to WETH-wei; the formula is dimensionally correct as written, verified rather than assumed.

Impact if unfixed: the "reserved" amount subtracted is wrong by exactly the ETH/USD price factor. At high ETH price, too little WETH is treated as reserved, so the pool can approve redemptions against collateral that isn't actually free. At low ETH price, the check over-reserves and rejects valid redemptions.

7. PIDController: TWAP mechanism, three implementations

  • Commits: 1aead3d (2025-03-10), 7d3f5c6 (2025-03-23), a1f89b4 (2025-03-31)
  • File: contracts/Oracle/PIDController.sol
  • Category: oracle design

Attempt 1 (1aead3d): block-indexed buffer seeded with fake history

Defect: all 11 seeded "history" entries hold the identical spot price. A TWAP's function is to average a spot price against genuinely independent past observations; a buffer pre-filled with copies of the current price is not an average until 10 real blocks have elapsed. Indexed by block count, not wall-clock time, so equivalent windows vary with block-time on any non-constant-block-time chain.

Also in this commit (verified via diff, not present before): require(eth_usd_price > 0, ...) and equivalents for BankX/XSD prices, closing a separate path where a stale or zeroed oracle read could propagate into mint/redeem math.

Attempt 2 (7d3f5c6): real cumulative-price TWAP, real-time clock

Standard Uniswap-V2 cumulative-price primitive, real-time-based rather than block-count-based. Brings the standard hazards of that primitive: UQ112x112 fixed-point range, overflow and wraparound bookkeeping on the accumulator.

Attempt 3 (a1f89b4): fixed-length rolling average, current implementation

Arithmetic mean of the last 10 samples, sampled at most once per 180s. Avoids the cumulative-price accumulator's overflow edge cases.

Manipulation-resistance analysis (current state): updatePrices() is public, with no access-control modifier, gated only by currentTime >= lastPriceUpdateTime + priceUpdateInterval. It has no same-block or same-transaction guard, so a transaction that moves the pool price and then calls updatePrices() can record a skewed sample, affecting roughly one tenth of the rolling average. Router.sol provides the actual manipulation bound: checkAndUpdateSafety(token_type, current_price, volume) runs on every swap path and reverts "Price manipulation detected" if deviationPercent = abs(poolPrice, referencePrice) * 10000 / referencePrice > price_threshold[token_type], with price_threshold[0] = price_threshold[1] = 1000 (10%, verified in Router.sol). The 10-sample, 3-minute window bounds how much a single block can move the average; the router's 10% deviation check is what actually bounds how much a single block can move the underlying price being sampled.

08a6001 (2024-06-05): CollateralPoolLibrary visibility, internal to public

The commit message ("Collateral Pool Library visibility modified") does not state a reason; no comment appears in the diff. The standard technical effect of the change: public/external library functions can be deployed once and linked externally instead of inlined into every caller's bytecode, relevant when a contract's own bytecode approaches the 24 KB (EIP-170) limit. Whether that was the motivation here is not something the repo settles: no libraries: {...} linking block exists in hardhat.config.js, and no deploy script references CollateralPoolLibrary for external linking, only test files do.
